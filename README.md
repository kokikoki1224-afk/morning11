# 日本株モーニング11 自動化（STEP8-B-3まで）

## STEP8-B-1〜B-3: AI分析（入力設計・モデル切り替え・2モデル比較）

**HTMLへの統合（STEP8-B-4）はまだ行っていない。** 2モデルの出力を実際に見比べてから本番モデルを決める方針のため、今回は「AIに渡す入力データ」「プロンプト」「モデル切り替え」「Opus/Sonnet比較モード」までを実装した。`--generate` はAIを一切呼ばず、STEP8-Aと同じHTMLを生成する。

### 役割分離（STEP2〜8-Aから維持）

| Python側が確定させるもの（AIに計算させない） | AIが担当するもの |
|---|---|
| 市場データ取得・前日比・bp計算・±0.2%等の閾値判定・5指標のスコア・総合スコア・JST変換・ニュースの24時間フィルタ・重複除去・表示件数の選定 | 複数材料の組み合わせ（ねじれ）の解釈、セクターへの波及、イベントの意味、ニュースの文脈づけ、見出し・リード文・総合判定文 |

AIは**計算結果を解釈する役割**であり、数値を再計算しない。プロンプトでも明示し、さらにコード側の数値ガード（`validate_numbers()`）でAI出力中の `%` / `bp` / `円` / カンマ区切り数値が入力データに実在するか検証して、実在しないものを警告として記録する。

### 使用モデル（正式なモデルID・設定から切り替え）

Anthropic公式仕様で確認した正式なモデルIDのみを使用している。**コードにハードコードせず `config/settings.json` の `ai.model` から読む**。

| モデルID | 入力/出力 単価（per 1M tokens） |
|---|---|
| `claude-opus-5` | $5.00 / $25.00 |
| `claude-sonnet-5` | $2.00 / $10.00 |

### 実行方法

```bash
export ANTHROPIC_API_KEY=xxxxx     # 環境変数のみ。settings.jsonやコードには絶対に書かない
python main.py --ai                # 設定のai.modelで1回だけ実行
python main.py --ai-compare        # compare_models（既定: Opus 5とSonnet 5）を同一条件で順に実行
```

**`--ai-compare` は実行したモデル数だけAPIコストがかかる**（通常実行の約2倍）。日々の運用では `--ai`（1モデル）を使うこと。

結果は `output/ai_run_YYYY-MM-DD.json` / `output/ai_compare_YYYY-MM-DD.json` に保存され（gitignore対象）、使用モデル・入力データ・AI出力・実行時間・トークン数・エラーの有無をローカルで見比べられる。HTMLへは自動公開しない。

### 比較の公平性

`--ai-compare` は**同じ日の同じ入力データ・同じプロンプト・同じ`max_tokens`**で各モデルを順に実行し、**変えるのはモデルIDだけ**。テスト（`test_compare_models_runs_each_model_with_identical_input_and_prompt`）で、2回の呼び出しの `system` / `messages` / `max_tokens` が同一かつ `model` だけが異なることを検証している。

### AIへの入力データ（`analysis/ai_analysis.build_ai_input()`）

海外5指標（Python確定のスコア付き）、日本3指標（`scored: false` を明示）、総合スコアと閾値ルール、今週の重要イベント（JST変換済み）、STEP7で取得したニュース（全カテゴリ・最大30件）、未実装指標（S&P500・NYダウ・日経平均）、データ取得エラー。**取得失敗した指標は `status: "取得失敗"` として値を入れずに渡し**、AIが推測で埋める余地をなくしている。

### プロンプト（`prompts/ai_analysis_system.md`）

コードにベタ書きせず独立ファイルで管理。主な制約：
- 与えられた入力データだけを根拠にする（存在しないニュース・イベント・数値・予想値を生成しない）
- 数値を計算しない（引用は可、再計算は不可）
- ニュースは**タイトルしか渡していない**ので、本文にない事実を断定しない
- 判断材料が足りなければ「判断材料不足」と明示する
- 断定的な売買推奨・煽り表現の禁止
- 各文章は **事実 → 解釈 → リスク** の順

### 出力（構造化JSON / Pydantic + `client.messages.parse()`）

`headline` / `lead` / `verdict` / `combination_analysis` / `overall_analysis` / `sector_analysis`（`sector`・`view`（追い風/逆風/中立/注目）・`reason`）/ `key_risks` / `event_watch`。セクターは `settings.ai.sectors`（半導体・AI・グロース・銀行・輸出株・内需・防衛・エネルギー・商社）から渡し、AIが勝手に増やさないようプロンプトで固定。

### 失敗時の挙動（アプリ全体は止めない）

| 事象 | 挙動 |
|---|---|
| `ANTHROPIC_API_KEY` 未設定 | `status="skipped"` として明示（`--ai`系は exit 1、他のモードは無関係に動作） |
| APIエラー・ネットワーク障害 | SDK既定のリトライ（2回・指数バックオフ）後、`status="error"` として理由を保持 |
| タイムアウト | クライアントに120秒を明示指定（SDK既定の10分は朝レポートに長すぎる） |
| 不正JSON・スキーマ不一致 | 部分的に壊れた文章を出さず `status="error"` |
| `stop_reason == "refusal"` | 同上 |
| いずれの場合も | 市場データ・スコア・イベント・ニュース・HTML生成は影響を受けない |

### テスト（`tests/test_ai_analysis.py` 20件、`python -m pytest` で114件全て合格）
実APIは一切叩かない。設定からのモデル切り替え、2モデルが同一入力・同一プロンプトになること、JSONパース、不正JSON・APIエラー・キー未設定時に異常終了しないこと、AI分析がスコアを変更しないこと、AI失敗時も市場データ/イベント/ニュースが無傷であること、数値ガードの検知を検証。

## STEP8-A: 「今週の重要イベント」の位置移動と「注目ニュース」のHTML表示

### 確定したセクション順序
```
海外市場（既存） → 日本市場（既存） → 今週の重要イベント（STEP6実装、位置をここに移動）
```

`templates/morning11.html`内の`<section>`ブロックの並び順を変更しただけで、CSS（`<style>`内）は無変更。

### ニュースの選定ルール（`data/news.py`の`select_for_display()`、AIは使わない）
- STEP7の`fetch_news()`が返す、24時間フィルタ・重複除去済みの全カテゴリのニュース（`us_market`・`other`含む）をそのまま入力にする
- **カテゴリ優先順位**（表示選定専用の新規設定`news.category_priority`。取得用の`news.keywords`とは別物）:
  `nvidia → semiconductor → ai → boj → fx → rates → japan_market → china → energy → defense`
- 優先順位の先頭カテゴリから順に、カテゴリ内は`published_at`が新しい順に**最大3件**（`news.max_per_category_display`）採用
- 全体の合計が**最大10件**（`news.max_display_total`）に達したら打ち切り（優先度の低いカテゴリほど採用件数が減る/0件になりうる）
- タイトルの内容から重要度を推測するようなロジックは入れない。カテゴリ優先順位と新しさだけの機械的な選定
- **`us_market`・`other`は`category_priority`に含まれないため「注目ニュース」欄には表示しない。ただしデータそのもの（`fetch_news()`の戻り値）からは削除しない**（`select_for_display()`は選定結果を新しいリストとして返すのみで、入力を変更しない。STEP8-B以降でAIがニュース全体を参照できるようにするため）

「今週の重要イベント」の`.tl`/`.ev`タイムライン形式ではなく、「スコアの付け方」と同じ`.note`カードを採用（ユーザー判断：ニュースは「時間の流れ」ではなく「ざっと重要情報を拾うもの」のため）。1つの`.note`内でカテゴリごとに`■ カテゴリ名`の小見出し＋`<ul>`を繰り返す。カテゴリの日本語表示名は`generator/html.py`の`CATEGORY_LABELS`で管理（例: `nvidia`→"NVIDIA関連"、`boj`→"日銀"）。日時は`published_at`と生成時刻から計算した相対時刻（「2時間前」等、`_relative_time_ja()`）で表示する。

## STEP7: ニュース候補の取得・重複除去・テーマ分類（HTML表示なし）

**今回はAI・HTMLのどちらも変更しない。** `data/news.py` を新規追加し、「RSS取得 → 直近24時間フィルタ → 重複除去 → テーマ分類（ルールベース） → データ構造化」までを機械的に実装した。`templates/morning11.html` と `generator/html.py` はSTEP7では一切変更していない（ユーザー指示により、HTML表示はSTEP8以降でAI分析と合わせて実装する）。STEP7ではAI APIも一切使用していない。

### 採用したニュースソース

| 項目 | 内容 |
|---|---|
| ソース | **Google News RSS**（`https://news.google.com/rss/search?q=<キーワード>&hl=ja&gl=JP&ceid=JP:ja`） |
| 無料/有料 | 無料 |
| APIキー | 不要 |
| 利用条件 | 非公式・無保証の仕様（Google側のRSSフィードの構造・提供が予告なく変わる可能性がある。取得したXMLのcopyrightタグにも「個人の非商用フィードリーダー用途」である旨の記載あり） |

### 利用するテーマ（キーワード→カテゴリのルールベース分類）

| 検索キーワード | category |
|---|---|

| 半導体 | `semiconductor` |
| 日銀 | `boj` |
| 為替 | `fx` |
| 金利 | `rates` |
| 米金融政策 | `us_market` |
| 日本株 | `japan_market` |
| 中国 | `china` |
| 原油・エネルギー | `energy` |
| 防衛 | `defense` |

未知のキーワードは `other` にフォールバックする（`VALID_CATEGORIES`に含む）。**この分類は意味解析ではなく、どのキーワードでヒットしたかをそのままカテゴリに写像するルールベース処理**であり、AIは一切介在しない（STEP8以降でAIによる意味的な解釈・要約を追加する前提）。

### 取得範囲・データ構造

- **直近24時間**（`news.recent_hours`、既定24）を基準とする。フィルタは記事自身の**公開日時（published_at）**に対して行い、取得を実行した時刻（fetched_at）と混同しない（`filter_recent()`で分離、テストでも確認）。
- 本文は取得・保存しない。保持するのは以下のみ：

```python
{
    "title": "...",
    "url": "...",
    "published_at": "2026-09-06T21:40:51+09:00",  # JST ISO8601
    "source": "...",
    "category": "ai",
    "matched_keyword": "AI",      # 追跡用の追加情報
    "feed": "google_news_rss",     # 追跡用の追加情報
}
```

- `fetch_news()`の戻り値は `{"news": [NewsItem...], "fetched_at": ISO文字列, "errors": [...]}`。

### 重複除去の方法（3段階、先勝ち）

1. **URL完全一致**
2. **正規化URL一致**（クエリ文字列・末尾スラッシュを除去して比較。同一記事がクエリパラメータ違いで複数キーワードにヒットするケースに対応）
3. **タイトルの類似度**（文字bigram＝2文字の滑り窓集合どうしの**重なり係数**（Overlap coefficient = |A∩B| / min(|A|,|B|)）で判定。日本語は分かち書きされないため単語トークン化ではなく文字bigramを採用。Jaccardではなく重なり係数にしているのは、「見出しの一部を包含する関係」（例：「半導体メモリー急伸」と「半導体株が上昇 半導体メモリー急伸で連想買い」）でも高スコアになるようにするため）

閾値（`news.dedup_similarity_threshold`、既定0.75）は、実際に無関係な記事同士を誤って統合しないことをテスト（`test_dedupe_does_not_over_merge_distinct_articles`）で確認した上で設定している。

### データ取得失敗時の挙動

- キーワードごとに独立して取得するため、**1つのキーワードのRSS取得が失敗しても他のキーワードの結果はそのまま返す**（エラーは`errors`に追記）
- 取得できなかった情報を推測で埋めることはしない（0件・エラーいずれの場合も架空のニュースは生成しない）
- 実行時のログ出力は `main.py` の `--test`/`--generate` に統合済み（`[ニュース候補（参考情報・HTML表示はSTEP7ではまだ行わない）]`）

### テスト（`tests/test_news.py`、`python -m pytest` で81件全て合格確認済み）
- RSSのパース（タイトルからのソース名重複サフィックス除去、URL、pubDate、ソース名の抽出）
- `max_items`による件数制限
- ネットワーク失敗時に空リスト＋エラーメッセージを返し、架空データを作らないこと
- pubDateのJST ISO8601変換、パース不能な値でNoneを返すこと
- 24時間フィルタ（境界値ちょうど24時間・25時間前・未来日時・published_at不明のケース）
- ルールベースのテーマ分類（既知キーワード全件・未知キーワードのotherフォールバック）
- 重複除去（URL完全一致・正規化URL一致・類似タイトルの統合・無関係記事の非統合）
- `fetch_news()`の統合動作（0件、一部キーワード失敗時の挙動を含む）

## STEP6: 今週の重要イベントカレンダーの自動化

**総合スコアには一切関与しない。** イベントの事実データ（日付・時刻・国・イベント名・重要度）の取得・JST変換・期間フィルタだけを行い、「このイベントが日本株にどう影響するか」の解釈はしない（AIは後続ステップで担当）。データ取得（`data/events.py`）→ main.py → HTML整形（`generator/html.py`）→ テンプレート埋め込み（`templates/morning11.html` の `{{EVENTS_TAG}}` `{{EVENTS_BLOCK}}`）という一方向の流れで、STEP2〜5と同じく取得と表示を分離している。

### 採用したイベントデータソース

| 対象 | ソース | 無料/有料 | APIキー | 自動取得の実態 |
|---|---|---|---|---|
| 米CPI・雇用統計(NFP)・GDP・小売売上高・PCE | **FRED公式API** `fred/release/dates`（release_id: CPI=10, 雇用統計=50, GDP=53, 小売売上高=9, PCE=54） | 無料 | 要（`FRED_API_KEY`、既存のUS10Y取得と共用） | **実際に毎回HTTPで取得**。発表日一覧を取得しJST窓でフィルタ |
| FOMC・日銀会合・日本GDP・日本CPI・鉱工業生産・中国PMI/GDP | `config/events_calendar.json`（手動メンテナンスの静的データ） | ― | 不要 | **自動取得ではない**。実在する公式発表予定（FRB・日銀サイト等で確認した日時）を人手で登録した固定データ。下記「調査したが採用しなかった候補」参照 |

### JST変換・日付またぎの確認

`_to_jst(date, time, tz_name)` で変換する。`tz_name`が`None`の場合（日本側の静的データ）はそのままJSTとして扱い、指定がある場合（米国データ）はタイムゾーン変換する。

### 表示対象・重要度フィルタ・0件/失敗時の挙動

- `config/settings.json`の`events.days_ahead`（デフォルト7）で「本日〜今後N日」を窓として抽出。窓外（過去・先すぎる未来）は表示しない
- `events.importance_filter`（デフォルト`["high"]`）で重要度フィルタ。空リストにすれば全件表示に変更可能
- **イベントが0件の場合**：「直近N日以内に登録されている重要イベントはありません」と明示し、架空のイベントは生成しない
- **取得が完全に失敗した場合**（例：`FRED_API_KEY`未設定）：「イベントデータ取得不可（エラー内容）」と明示する
- **一部だけ失敗した場合**（例：静的カレンダーは成功したがFRED側が失敗）：取得できたイベントはそのまま表示し、末尾に「一部のイベントソースが取得できませんでした（エラー内容）」を追加する。実際に`FRED_API_KEY`未設定の状態で`python main.py --generate`を実行し、この表示になることを確認済み

### 1. 日経225先物（NKD=F）の基準時刻検証

USD/JPYと同様、**単純な日足Closeは採用していない。** 時間足(`interval="1h"`)をJST変換して実データを検証した結果、次のことが分かった。

- CME（Nikkei/USD先物）には**JST06:00〜07:00頃に日次メンテナンス休止**があり、その前後で明確なバーの断絶がある（例：`...05:00`の次が`07:00`に飛ぶ）。
- 月曜日はこの休止がさらに長く、JST07:00（＝日曜17:00 CT、CME週間再開時刻）まで一切バーが無い。これは「日本株寄り付き前」が実質的に生成される時間帯（JST7:00前後）と、CMEの日次区切りがほぼ一致していることを意味する。
- yfinanceの**日足`Close`もこの検証と矛盾しない**（USD/JPYのような時系列上ありえない値は出なかった）。ただし日足の「Date」ラベルはニューヨーク時間の暦日で付与されており、実際の内容はJST翌朝5時台まで続くため、ラベルだけを見ると「どの朝の値か」を誤解しやすい。
- そこで**JST05:00台バー（休止直前の最終バー）のCloseを「その営業日の代表値」として明示的に切り出す方式**を採用した（USD/JPYと同じ`_yfinance_hour_snapshot`を`tz="Asia/Tokyo", hour=5, field="Close"`で再利用）。これにより「日足のCloseだから採用」ではなく、「休止直前＝大取夜間取引終了に相当する、朝の判断に意味のある値」であることを明示的に保証している。

**実測による裏付け**：2026-09-05のJST05:00台バーのCloseは**65,820**。これは前回セッションで手動確認した実際の大取夜間取引清算値（**約65,830**）とわずか10円（0.015%）差で、CME先物（ドル建て）とOSE先物（円建て）の建値差として十分説明できる範囲。日足`Close`ベースでも同じ65,820が得られており、今回の検証範囲では両者は一致した（ただし前述の通りラベルの意味が分かりにくいため、明示的なJST05:00スナップショット方式を正式採用とする）。

### 2. TOPIX連動ETF（1306.T）

STEP2で`^TOPX`・`^TPX`が取得不可（データなし）と確認済みのため、**TOPIX指数そのものではなく連動ETF「NEXT FUNDS TOPIX連動型上場投信」（1306.T）を代理指標として採用**。東証の単一立会時間（9:00-15:00 JST）内の通常の日足Close/Openで前日比を計算しており、USD/JPYや日経225先物のような基準時刻の曖昧さは無い。**HTML上でも指標名を「TOPIX連動ETF（1306.T）」と明記し、指数そのものと同一ではないことが常に分かるようにした**（`templates/morning11.html` の固定テキスト）。ETFの価格変動率は指数のそれとほぼ一致するが、分配金落ち・信託報酬・需給要因により完全一致はしない点に注意。

### 3. 日本10年国債利回り（財務省公式CSV）

候補どおり**財務省「国債金利情報」公式CSVを採用**（無料・公式・APIキー不要）。当月分の軽量CSV（`jgbcm.csv`、Shift-JIS/CP932エンコード）を第一候補とし、月初などで当月分が2行に満たない場合のみ全期間CSV（`jgbcm_all.csv`）にフォールバックする。日付は「R8.9.3」のような和暦（令和/平成/昭和）形式のため、`_era_to_iso_date()`で西暦ISO形式に変換している。10年債の列は基準日を含めて11列目（0始まりで10番目）。前日比は**％ではなくbpで扱う**（`change_bp`フィールド、他の利回り指標と同じ構造）。公式CSVは実際の取引日より1日程度遅れて公表される場合があり、今回の検証でも他の指標が9/4時点なのにMOFデータは9/3時点までだった（米10年債のFRED同様、公式データの公表ラグとして許容する）。

## スコア計算（STEP3）

対象は Nasdaq / SOX / 米10年債利回り / USD/JPY / KOSPI の5指標（実装: `analysis/score.py`）。データ取得（`data/market.py`）とスコア判定（`analysis/score.py`）は責務を分離しており、スコア計算はネットワークアクセスを一切行わない。

- ±0.2%ルール（Nasdaq/SOX/USD-JPY/KOSPI）：`change_percent >= +0.2` → `+1`、`<= -0.2` → `-1`、それ以外 → `0`
- 米10年債はbp閾値・符号反転：`change_bp <= -3` → `+1`（金利低下は好材料）、`>= +3` → `-1`、それ以外 → `0`
- 欠損指標（`status != "OK"`）は**推測値を入れず、スコアに加算しない**。`available`（取得できた指標数）と`total`（5）を必ず保持し、一部欠損時は`provisional=true`として「4/5指標取得・暫定スコア +3」のように表示する
- 総合判定：`+3〜+5`→追い風、`-2〜+2`→中立・やや方向感なし、`-5〜-3`→逆風

テスト（`tests/test_score.py` `tests/test_market.py` `tests/test_generator.py`、`python -m pytest` で49件全て合格確認済み）：
- ±0.2%ルールの境界値（+0.3/+0.2/+0.19/0/-0.19/-0.2/-0.3 → 1/1/0/0/0/-1/-1）
- 米10年債bp閾値の境界値（-4/-3/-2/0/+2/+3/+4bp → 1/1/0/0/0/-1/-1）
- 欠損指標が0点ではなく「加算されない」ことの確認、`available/total`の整合性
- USD/JPY・日経225先物が日足関数を呼ばず時間足スナップショット関数を呼んでいることのモック検証
- 財務省CSVのパース（和暦→西暦変換、10年債列の抽出、当月分不足時の全期間CSVへのフォールバック）
- 日本市場3指標の取得失敗が海外5指標のスコアに一切影響しないことの確認

### USD/JPYの基準時刻問題（調査結果と対応）

**問題**：yfinanceの`JPY=X`日足（`interval="1d"`）は、24時間ほぼ連続で取引されるFXペアの集計区間があいまいで、実際に時間足と突き合わせたところ、日によっては前日比の符号（円高/円安）が逆転するほどの不整合を確認した。

検証例（2026-09-02〜09-03、時間足ベースで正しい値動きを追った場合）：
- 日足`Close`の系列：9/1=159.747 → 9/2=**160.196**（前日比+0.28%＝円安） → 9/3=158.923
- 同じ期間を時間足(1h)で丁寧に追うと、9/2の実際の値動きは159台からザラ場で158円台へ**下落**しており、日足の「9/2=160.196」という値は時系列上ありえない（前後のどの時間足バーにも該当する値がない）。yfinanceの日足エンドポイントが、24時間連続取引銘柄で内部的に取り違えている可能性が高い。

**対応**：日足を使わず、時間足(`interval="1h"`)を取得し、日本の為替報道が慣行的に「その日の終値」として扱う**NY17:00（米東部時間）**に最も近いバーの始値を「その日の代表値」として採用し、前日の同時刻との差分でスコア判定する。これにより時系列上の整合性を確認済み（例：9/2のNY17時値=158.674、9/3のNY17時値=155.779〜155.848）。

**残る限界**：日本の為替速報記事（外為どっとコム等）が引用する「終値」は、記事執筆時点のアドホックな時刻を指すことが多く、NY17:00ちょうどとは数十分〜1時間程度ズレることがある。今回の検証でも0.3〜0.5円程度の差が残った。これは「NY17:00」という一貫した基準を採用したことによる説明可能な差であり、日足エンドポイントの不整合（符号が逆転しうる）とは性質が異なるため許容する。

**運用上の注意**：本番（GitHub Actionsで日本時間朝に実行）では前営業日のNY17:00は確実に経過済みのため問題ないが、当日の途中経過を見るような使い方をすると直近日のスナップショットが未確定になる場合がある。

日経225先物・TOPIX連動ETF・日本10年債の検証詳細は上記「STEP5: 日本市場3指標の追加」を参照。

## 不採用にしたソース
- **Stooq**：計画時点では無料・安定という評価だったが、実装して直接叩いたところ2026年9月時点でJavaScriptベースのbot対策チャレンジ（Cloudflare的な検証）が導入されており、単純なHTTPリクエストでは機械的に取得不能と判明。当面はyfinance一本に統一。
